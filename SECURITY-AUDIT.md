# HORIZON security audit — initial findings

Scope: repository `CHARTECH2024-web/Charles`, branch `main`. This is a source-code review and emulator test setup, not a penetration test of production services. No production Firebase rules or Cloudflare deployment are changed by this audit branch.

## Architecture found in source

- Firebase Authentication uses Google sign-in and a shared browser session.
- Cloud Firestore stores profiles, conversations/messages, business records, and public media/document metadata.
- The frontend uploads media and raw documents directly to Cloudinary using an unsigned upload preset.
- Firestore stores Cloudinary delivery URLs and metadata.
- The checked-in `firebase.json` declares Firestore rules but does not declare a Firebase Storage rules file. The application code explicitly says it does not use Firebase Storage.
- No `wrangler.toml`, `wrangler.json`, or `wrangler.jsonc` was found at the repository root. The Worker’s deployed configuration and response headers cannot be verified from this repository alone.

## Important mismatch to resolve

The Firestore rules pasted from the Firebase console earlier in this conversation do not match the current `main/firestore.rules` retrieved from GitHub. The current repository version contains stricter validation for business records and messages, and it disallows message updates; the pasted rules allow broader business operations and message updates. Do not deploy either copy until the live Firebase rules, repository revision, and expected app behavior are reconciled.

## Findings

### High — Cloudinary assets are not made private by Firestore visibility

The frontend stores `secure_url` from Cloudinary in Firestore. Setting a Firestore metadata field to `visibility: "private"` only hides the metadata from ordinary Firestore reads. It does not revoke or protect the underlying Cloudinary delivery URL. The current UI's “private” toggle therefore must not be treated as access control for the file itself.

Before supporting private chat attachments, use a server-side authorization design for private delivery (for example, authenticated/signed delivery generated by a trusted server component), and verify that direct unauthenticated requests to an asset are denied. Do not put Cloudinary API secrets in browser code.

### Medium — Unsigned Cloudinary upload preset is public

The cloud name and unsigned preset are embedded in frontend code. These are not API secrets, but anyone can attempt uploads through that preset. Enforce strict allowed formats, size limits, folder restrictions, and any available abuse controls in Cloudinary itself; client-side checks alone can be bypassed.

### Medium — Conversation creation lacks accepted-request workflow

The checked-in rules allow a signed-in user to create a conversation document containing two distinct user IDs, as long as the creator is a participant. The current `community.js` creates the conversation immediately when a member opens another member. There is no conversation-request/acceptance model in the current client code or rules.

This needs a coordinated rules + client design; changing rules alone would break the current chat flow. Add it before releasing the planned request/accept/reject/block experience.

### Medium — Message deletion semantics are incomplete

The current UI deletes a message document on double-click. The checked-in rules allow a sender to delete their own message but do not enforce a 15-minute cutoff, and there is no per-user “delete for me” state. A rules-only change cannot safely implement the full desired behavior without changing the data model and client UI.

### Positive controls observed in checked-in rules

- Private profile reads are limited to the profile owner and admin.
- Conversation/message reads require membership in the conversation.
- Message creation checks that `senderId` equals the authenticated UID and that the receiver is another participant.
- Business records are scoped by business owner UID, with constrained create/update fields and transaction-linked stock/sales/debt rules.
- Media/document metadata creation, updates, and deletion are admin-only; public reads depend on `visibility == "public"`.

## Test plan

The emulator suite covers unauthorized conversation reads, participant reads, sender spoofing, cross-owner business reads/writes, public/private metadata visibility, and non-admin media/document writes. Two planned behavior tests are explicitly skipped until the request-acceptance and message-deletion data models are implemented. Passing these emulator tests does not verify Cloudinary access control, Firebase production deployment, or Cloudflare Worker headers.

## Safe next steps

1. Compare the actual deployed Firestore rules with the checked-in `main/firestore.rules` and identify the intended release revision.
2. Run the emulator test workflow and fix any failures without deploying to production.
3. Decide whether all Cloudinary assets are intended to be public. If not, implement private delivery through a trusted server-side component and verify direct-URL denial.
4. Implement conversation requests and message deletion semantics together with their rules and tests.
5. Verify the Cloudflare Worker configuration and HTTPS/security headers in the Cloudflare dashboard before changing deployment settings.
